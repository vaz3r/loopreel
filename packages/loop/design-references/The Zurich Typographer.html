Precision Is a Shared Language.

Abstract

An interface is where decisions become visible. A design system should make those decisions traceable: from visual intention to semantic token, from component behavior to release criteria. The ambition is not identical screens. It is a shared grammar precise enough to implement—and explicit enough to challenge.

BYLINE The Zurich Typographer — an editorial on design systems and engineering
PEER REVIEWED

Define. Encode. Verify.

THREE COMMITMENTS
01

DEFINE THE LANGUAGE

Name the intention, not merely the appearance. A crimson value describes a color; a semantic token declares its purpose. Establish a vocabulary for roles, states, and relationships so that design and engineering can discuss the same decision without translating it from a screenshot.

02

ENCODE THE DECISIONS

Treat each component as a versioned agreement. Specify its states, interaction behavior, accessibility requirements, and permitted variation. Give exceptions an owner and a review date: a departure should be a conscious decision, not an undocumented inheritance.

03

VERIFY THE OUTCOMES

Separate a persuasive system from a demonstrated improvement. Establish the baseline, instrument a bounded pilot, and compare equivalent work. Measure adoption alongside divergence, change time, and accessibility regressions. Publication of the library is a delivery milestone—not evidence that the system works.

Make Consistency Observable.

MEASUREMENT / PENDING BASELINE
—% TOKEN ADOPTION

Proposed measure: eligible style declarations using approved tokens divided by all audited eligible declarations, multiplied by 100. Record scope, exclusions, and audit date before reporting.

—% COMPONENT REUSE

Proposed measure: eligible interface instances implemented with approved shared components divided by all audited eligible instances, multiplied by 100. Declare eligibility and component versions before counting.

—days MEDIAN CHANGE LEAD TIME

Proposed measure: median elapsed calendar days from an accepted change request to production deployment. Compare equivalent task scopes; report the observation window and completed-change sample.

—regressions / release ACCESSIBILITY REGRESSIONS

Proposed measure: newly introduced, confirmed accessibility defects in each audited release. Hold test coverage and severity definitions constant; an unmeasured release is not a zero-defect release.

THE DOCUMENTED RECORD

Pending pilot evidence.

Coherent variety is the editorial ambition, not an established result. Test semantic tokens in one proposed button-system pilot while retaining a comparable baseline. Before implementation, define divergence as departures from the agreed component contract and specify the comparison method and rejection criterion. Keep task scope, acceptance criteria, and test environment comparable. Reject the null only if the measured difference meets that criterion; assess implementation time and accessibility defects separately for trade-offs.
